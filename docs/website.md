# Website: pages, photos, video, apps

Detailed notes moved from CLAUDE.md. Read the section for the feature you are changing; keep it current when behaviour changes.

- `content/<page>.md` = pages (add a file = add a page; `##` headings get anchors; `fold: yes` makes each `##` section tap-to-open on phones, used by Our Rides). Admin edits override the GitHub version (revert per page). Formatting: `content/README.md`. Placeholders: `{strava}`, `{kit}`, `{pay_link}`.
- **Card editor** (the page editor's default, "Easy editor"): `cardEditor()` in the `page-edit` template parses the Markdown into cards (settings, title, paragraph, section heading, columns from `###` runs, photos, buttons, lists, ride details, notes, club pieces like `{membership-plans}`) and writes it back into the same textarea, so saving/preview/GitHub are unchanged. Cards keep their original lines until edited (untouched pages save byte-for-byte); anything it can't represent becomes a raw "Text" card. Paste keeps only bold/italic/links. Round-trip check in the browser console on an edit page: `f=document.getElementById('page-form').cards; f.text(f.parse(src))===src`, and `f.rewrite(f.parse(src))` should preview the same. "Edit as text" switches to the old editor (remembered per browser).
- **Page editor** (Website → Pages, "Edit as text"): toolbar types the Markdown marks (Bold, headings, lists, link box, Insert… for columns/fact tables/placeholders), Ctrl+B/I/K/S, unsaved-changes warning. Live preview posts the text to `/admin/pages/<file>/preview`, which draws the page with the real templates minus scripts and animations into a sandboxed frame; nothing is saved.
- **Uploads:** JPG/PNG resized to ≤2000px, EXIF stripped, saved as JPG (PNG with alpha stays PNG); WebP/GIF kept. Max 20 MB; every upload box shrinks photos in the browser first (`web/static/photos.js`, inlined into site.js's page script and the admin pages), so big iPhone photos go up as ~2000px JPEGs. Server keeps ≤2000px at quality 86 (steps down to 1800/1600 past 800 KB). Gallery adds 1440/960/480 copies (missing ones made at startup, `sizeOldPhotos`). Every handler that takes files calls `allowSlowUpload(w)` (main.go) before reading the form: the server's 30 s request / 60 s answer limits otherwise cut off a batch of photos sent on a phone signal (10 minutes instead; the video upload sets its own hour). Names typed on public forms go into admin and club-inbox emails through `mailLiteral` (emailfmt.go), so they never become links.
- **Photo framing** (`focus.go`): cropped photos store `"x% y%"` or `"x% y% zoom"` (zoom 1–4); `focusStyle` draws it (object-position, plus scale + clip-path when zoomed; rounded boxes set `--r` in site.css). One admin tool everywhere: `openFraming` in admin.html (drag, zoom, live previews of each shape in `FRAME_SHAPES`; `framingStyle` mirrors `focusStyle`). Used by home photos, board, newsletter photos/strips, gallery photos (`focus-<id>`, autosaved), and page photos (`![alt](photos/x.webp#focus=40,30,1.5)`).
- Home video (`herovideo.go`, `Store.HeroVideo`; Website → Home photos → Top video, board): two finished uploads made in an editor, **Computer video** (wide, best 1920×1080) and **Phone video** (tall, best 1080×1920), AV1 only, about 3,000 kb/s (`heroKinds`, `bestVideoRate`). **Never re-encoded:** `uploadHeroVideo` streams the upload to `data/video-uploads` (not served: camera files carry GPS), checks it with ffprobe (`probeClip`: must be AV1, `err=video-codec`; computer wider than tall, phone taller than wide), then copies only the picture into an MP4 with `-c copy` (no sound/subtitles/data tracks/chapters/metadata, `+faststart`), takes a `.jpg` still of the first frame, and puts it live at once (`computer-<stamp>.mp4`, `phone-<stamp>.mp4` in `data/media/video`). `HeroFile.Type` carries the exact codec (`av1Type`: `av01.profile.levelM.depth`); `videoWarnings` (bigger/smaller than best, over 4,500 kb/s, over 60 s, HDR) show on the admin page but never stop an upload. Home page: `<source media>` picks phone (≤767px) or computer; no phone video = phones play the computer one cut to fit, no computer video = computers show the top photo. Browsers that can't play AV1 (older iPhones/Macs), data saver, and a computer with only a phone video keep the still under it (site.js removes the `<video>` when no source `canPlayType`); reduced motion gets the top photo. Off = the top photo. `cleanVideoFiles` at startup deletes every file in the video folder no video uses (older versions' clips and loops) and the uploads folder. ffmpeg/ffprobe: `FFMPEG` env names ffmpeg if it isn't on PATH; deploy/setup.sh installs it; the page warns when it's missing.
- Photos: `content/photos/hero.webp` (~2000px, plus square `hero-phone.webp`), `ride.webp`, `giving.webp` (~1000px). Admins can replace the home page's top photo on Website → Home photos → Top photo (`hero.go`, `Store.Hero`; one upload with one framing for every screen; phones get `Hero.Phone`, an 800px square cut at the framing by `heroPhoneCrop`, remade on each save and at startup if missing; empty = the built-in hero files).
- **Member photos** (`/share-photos`): spam checks (honeypot + form token), 5 sends/hour/IP, queue cap 300, stored in `data/submitted`, reviewed at Website → Photos to review (one card per sender, all ticked; Approve/Reject in place with Undo; rejected kept 30 days, purged when the page opens). **Sharing into an album:** every album on `/gallery` (featured one too) and each album page link to `/share-photos?album=<id>`; for a visible album the share page then shows the album's name under the title and sends it in a hidden `album` field instead of the picker (a hidden or unknown album falls back to the picker). Same spam checks, limit, review queue and PIN rules; the review card has that album picked, and Approve puts them there. **Removing photos** (album admin page, `galleryremove.go`): each photo has a round trash button (`.photo-x`, `do=remove:<id>`, POST); with JavaScript the photo goes in place and a dark toast (`.ed-toast`) offers Undo for 12 s, covering every photo removed since it appeared (`do=restore:<ids>`); without, the page comes back with `?removed=<ids>` and an Undo flash. Ticked photos can be removed together the same way. A removed photo moves to `RemovedGallery` (with its place in the album) and its files to `data/removed`, so it's off the website at once; Undo puts it back in its place; it's deleted 30 days later when Gallery or an album opens (`purgeRemoved`). Removing a member's shared photo marks it Rejected on Photos to review (so it doesn't come back as waiting); Undo clears that. Undoing an approval on Photos to review still takes the gallery copy out for good. **The gallery is the photo library:** the newsletter editor's, Board page's and Home photos' (top photo and photo row) "Choose from the gallery" (`/admin/gallery/pick`, `/admin/newsletter/from-gallery`) and an album's "Add to newsletter" copy photos into an issue (own copy, so removing from the gallery never breaks a sent issue). Public wording is always "Share your photos". **Albums** (Website → Gallery): dragged into order, one can be featured (`Album.Featured`, shown first and big on `/gallery`), and hidden ones (`Album.Hidden`) are off `/gallery`, their pages, the sitemap and the share page's album list but stay in the newsletter's picker. List toggles answer in JSON with the list re-rendered (`album-list` template) and an Undo; an album's captions and order save as they change. **Club PIN** (Security → Club PIN & access) skips review for photos and ride submissions; 10 tries/hour/IP; also lets ride leaders step down/cancel.
- **Minutes:** uploaded on admin Minutes; listed at `/minutes` (unlinked, noindex: open to anyone with the link, `/minutes#m<id>` per meeting, Copy link in admin). Word uploads become PDFs via headless LibreOffice when installed (`docpdf.go`; profile in `data/office-profile`); the .docx is kept as `original`; Word files from before are converted at startup.
- **Instagram:** via Behold JSON feed (Meta's API route was abandoned). Admin Instagram tab → paste feed URL → Connect. Polled every 3 h (free plan: 6 posts, 1,200 reads/month). Falls back to Instagram embeds for posts outside the feed.
- **Home screen app** (`app.go`, `web/static/sw.js`): `/manifest.webmanifest` (standalone, icons `app-192.png`/`app-512.png` used as any and maskable; `apple-touch-icon.png` 180px; a close-up of logo-light.svg on tarmac.jpg, the stripes running off both edges, drawn with headless Edge; shortcuts Calendar, My Membership, Ride Waiver). The service worker is `/sw.js` (no-cache; `__V__` = site version, a new version empties its caches), registered by site.js: pages come from the network first and a copy is kept (newest 40) only for public pages with no query but `?m=`; `PRIVATE` in sw.js lists what's never kept (admin, membership, RSVP, kit, forms, token links). With no signal: the kept copy, else `/offline` (saved at install). Versioned `/static/` files are kept too. It's the base for push notifications.
- **Admin app** (`adminapp.go`, `admin-app` template, `.app-*` in admin.css): admin pages link `/admin-app.webmanifest` (outside `/admin`: browsers fetch manifests without cookies; scope `/admin`, start `/admin/app?app=1` (shortcuts carry `?app=1` too; `id` stays `/admin/app`), "PV Admin", black-P icons `admin-192/512.png`, `admin-touch-icon.png`, drawn like the public icon but logo.svg on white), so adding an admin page to the home screen gives a separate app. `/admin/app`: a **search box** at the top (`appsearch.go`, `app-results` template, `.app-search`/`.app-found`): 2+ letters ask `/admin/app/search?q=` as typed (200 ms) and the results replace the rest of the page (`body.app-searching`); without scripts it submits to `/admin/app?q=`. Every word must match: members by name or email, rides and events (held ones, then the next 8 weeks soonest first, then the last 4 weeks latest first) by name, place or kind, RSVP invitations by title or place; up to 8 of each, linking to the admin page (all three open to website admins; a member page is read-only for them). Then Needs you (`attentionFor`), next 3 rides, then button rows, the first being **Jobs** (`appjobs.go`, `app-today`/`app-approvals`/`app-paid` in admin-app.html): **Rides today** (`/admin/app/today`: today's and tomorrow's rides, with a Note box and Ride is on / Cancel / Put it back posting to `/admin/rides/{key}/cancel`; badge = today's uncancelled rides), **Approvals** (`/admin/app/approvals`: the Needs you lines that have buttons; badge = their count) and, for the board, **Mark paid** (`/admin/app/paid`, boardOnly: every member whose dues aren't paid, website joiners first, newest first, then lapsed members by last paid year, with a name filter; badge = joiners waiting). Each is a plain admin page in whichever frame is set, over the computer's handlers, whose buttons send `return=` their own path (`listReturns`, `homeReturn`). After Jobs come the other button rows on a dark page (`appTiles`, groups of 3 with badges, each group its own color via `Key` → `.g-rides` etc.; `boardHref` drops board screens for website admins). **App frame** (`appframe.go`): the server, not CSS, picks the frame. `?app=1` on any `/admin` URL sets the `pv_app` cookie (`1`, path `/admin`, HttpOnly, SameSite=Lax, Secure on https, 400 days, no identity: functional, admins only, so no banner) even when logged out; `?app=0` clears it. Either way (GET only) it then redirects to the same page without `app=`, so reloads and copied links don't carry it. `inApp(r)` (the cookie) sets `adminView.InApp`: the head template then draws the `.app-top` Home bar (an `.app-back` pill, chevron + Home, then the page title) in place of `<header class="bar">`, the section row stays; the foot script slides `.bar` away on scroll but leaves the Home bar in place; `GET /admin` redirects to `/admin/app` keeping `ok=`/`err=`. The app home's foot row has **Full menu** (`/admin?app=0`) for a browser that shares cookies with the installed app (Android). No `display-mode` rules or JS redirect. `TestAdminAppFrame` and `TestDemoClubAdminPages` (every page again with the cookie) cover it. **Admin alerts** (`adminpush.go`, `Store.AdminPush`): "Alerts on this phone" at the foot of the app home (buttons first, then Needs you, Next rides): Turn on alerts registers `/admin/sw.js` (the same script as `/sw.js`, scope `/admin/`, so the admin app has its own subscription apart from the club app's ride alerts) and posts to `/admin/push/subscribe`, tying the phone to the logged-in admin (`AdminPushSub.Admin`; the setup password gets no Alerts section, 403); switches per kind (`adminAlertKinds`: requests, rides (held rides + loaner requests), photos, members (board only, `boardOnlyKinds`), riders ("I'm in"), waivers (board only); `Off` = turned off; riders and waivers are `optInKinds`: they start off and `On` lists them once turned on) post to `/admin/push/kinds`; only the owner can read/change/forget a phone. Sent by `alertAdmins(kind, m, ttl, who)` through `pushSend` with `Icon` admin-192: `alertHeldRide` (calendar.go), `alertLoaner`, `alertPhotos` (only photos going to review), `alertRequestSent` (only `wantsAnswer` admins), `alertRequestSettled` (the sender, from `mailRequestSettled`), `alertSignup` (public.go), `alertRiderIn` (imin.go: a new rider; one alert per ride, `Tag` in-<key>, body says how many are going), `alertRideWaiver` (ride and loaner waivers) and `alertMemberWaiver` (membership-page waivers, adult or under 18, and the join form's, in one alert; only new ones, not a repeat the store returns). **Alert buttons** (`pushMsg.Actions`, `alertActions`): held rides (Approve), loaner requests (Confirm) and spending requests (Approve) carry that button plus Look first. sw.js keeps them in the notification's data; a press posts `return=/admin/app` to the same route as the Needs you button (`/admin/rides/{key}/approve`, `/admin/loaners/{id}/confirm`, `/admin/treasurer/requests/{id}/approve`; only `/admin/…` paths) with the admin's login cookie and `X-Alert-Action: 1`, so `auth`/`boardOnly`/`wantsAnswer` apply as usual and `back()` answers `{"to": …}` instead of redirecting: `ok=` → a "Done" notification (`Done`, e.g. "Approved: Hilly Loop"); anything else (logged out 401, `err=`, no signal) opens the page. A plain tap (iPhones show no buttons) opens `URL`: the ride's admin page, `/admin/loaners#q<id>`, `/admin/treasurer/requests#r<id>`. `pushsubscriptionchange` posts to `/push/subscribe` with `old`; an admin phone is moved there (`MoveAdminPush`) instead of becoming a ride-alert phone. `DeleteAdmin` forgets their phones; backups leave them out. The browser pane can't test push: test on a phone.
- **Stats:** counts only by design; no per-member tracking. Weekly visitor codes are salted hashes kept until week end; emails use random per-copy tracking codes not tied to members.
- **Needs you buttons** (`attentionAct` in attention.go, `needs-acts` template): Home's Needs attention and the app's Needs you list each waiting thing on its own line with buttons that do it in place: a held ride → Approve, a waiting loaner request → Confirm / Decline, a spending request this admin answers → Approve (Reject needs a reason, so it stays on Requests), and on the app only (the computer Home has its Members card) a website joiner not marked paid → Mark paid (board). Each posts `return=` the list it is on (`withReturn`; `/admin`, `/admin/app` or a Jobs screen, `listReturns` in appjobs.go) and the handler goes back there with its usual `ok=`/`err=` (`homeReturn`; any other `return` is ignored). No Undo: each sends its email at once. Board-only buttons are dropped for website admins in `attentionFor`. Rides this week with an open leader spot are listed too, except events, cancelled rides and community rides (not the club's to lead).

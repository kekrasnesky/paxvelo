# Admins, members and dues

Detailed notes moved from CLAUDE.md. Read the section for the feature you are changing; keep it current when behaviour changes.

- **Admins:** email + password (PBKDF2). Setup password `ADMIN_PASSWORD` works by name until the first admin sets a password; afterwards it is only an emergency key (logged as `admin login with the setup password as …`). **Levels** (`permissions.go`): website admin (rides/calendar, ride-and-event emails only: `sendAll` forces `topic=events`, photo review/gallery, minutes view, read-only member lookup incl. emergency contact, own spending requests and receipts), board (everything else: routes wrapped in `a.boardOnly`, incl. deleting members/waivers, automations, club PIN) and president (`a.president`: Board page save, add/remove admins, send admin links, backup). Template flags `IsBoard`/`IsPresident` are set in `renderAdmin`; the menu drops `boardTabs` for website admins. `TestAdminRoutesHaveALevel` fails if a new `/admin` route uses plain `a.auth` without being listed in `websiteAdminRoutes`. `TestDemoClubAdminPages` opens every admin screen with the demo club as a website admin, a board member (Secretary) and the president: board-only screens must send a website admin Home with `err=board-only`, and no screen may show a link or form whose route (read from main.go) refuses that login, e.g. Mark paid, Upload minutes, links to Board/Automations/Security, or the Board page's form for anyone but the president (others get it read-only, in a disabled fieldset). It also checks `boardHref` agrees with main.go. Templates hide such controls with `.IsBoard` / `.IsPresident`. **Board roles** (`boardroles.go`) come from Website → Board: each `BoardMember` can be tied to a member record (`Member` id, picked in a "Member" select that marks admins with a gold crown (`crown` in icons.go; the select uses `appearance:base-select` where supported, else a plain ♛); the name shown on the page stays separate, e.g. "Gabe" for Gabriel). An admin holds a role when the tied member's email or name matches theirs (untied: the Board page name matches); `linkBoard` tied same-name people once (`BoardLinked`). Anyone on the board, the president or the setup password sees the Treasurer tab (`canSeeMoney`; routes use `a.boardOnly`, others go Home with `err=board-only`); a role containing "Treasurer" or the president removes its lines and saved reports (`canRemoveMoney`, `a.treasurerOnly`). The Admins page shows each admin's roles as tags. The president's own powers stay with Make president. Sessions last 30 days; removing an admin or changing a password logs them out.
- **Member page** (`/membership?t=`): My Membership is in the main menu and the footer. Opening a member's link sets an HttpOnly `pv_member` cookie (path `/membership`, 400 days, holds their token), so plain `/membership` opens their page on that device; "Sign out of this device" (`POST /membership/forget`) clears it; without it `/membership` asks for their email. A summary at the top shows dues (with the date an admin marked them paid, `Member.PaidOn`), the waiver and their details, each done or to do the same way; forms only below. Its link is in every club email and gets forwarded, so it shows the phone and emergency contact only in part (last 4 digits, first name and initial); boxes left blank keep what's on file. Test emails use the token `test` (`testToken`), whose My membership and Unsubscribe links open a "That was a test email" page. **Email check:** a website joiner, or someone renewing on `/join` after unsubscribing, is `Unconfirmed` and gets a "Confirm your email" email (`sendConfirm`: Confirm button to their page, PayPal link, the next on-the-road rides for their join-form answer). Club emails skip them (`Emailable`) until they confirm: the email's button opens `/membership?t=…&confirm=1`, whose script presses Confirm (`POST /membership/confirm`, redirects back to the page) for them. Loading the link alone never confirms, since email scanners open links. Each confirm email ends with a no-action-needed line for anyone not expecting it, which also turns emails back on for a returning member; so does Turn club emails back on (the link proves the inbox). Paying and Mark paid never wait for it; an admin adding the address confirms it. Confirm and My-link emails go through `SendMine` (My membership link at the foot, no Unsubscribe).
- **Family riders** (`household.go`): each other adult on a Family plan is in `Member.Household` (their waiver link) and also a member record with `FamilyOf` = the plan holder, sharing that link token, so club emails reach them. `save()` copies the plan's `PaidYears`/`PaidOn`/`Plan` onto riders (`syncRiders`); dues income and the unsigned-waiver list skip riders; a rider's waiver is the household waiver (`householdSigned`). Add, edit and remove from the member's admin page (`saveFamily`, board). Deleting the plan holder deletes riders; deleting a rider takes them off the plan (`expandFamily`). `ensureRiders` makes missing riders at startup.
- **Newsletter without joining** (`newssignup.go`): name + email on `/newsletter` (empty page, and a "Get it by email" section above every issue's colophon, not in previews) post to `/newsletter/subscribe` (same origin, honeypot, form token rendered into the cached newsletter pages, 5/hour/IP, 3/hour/address). A new address becomes an email-list-only member (no plan, `newsOnly()`), unconfirmed until it presses Confirm in "Confirm your PaxVelo newsletter" (`sendConfirm`, no pay line); an unsubscribed one gets the welcome-back Confirm; one already getting emails gets nothing. The page says "Check your email" for every address.
- **Email choices** (`emailtopics.go`): members switch off the Newsletter or Calendar events on their page (`NoNewsletter`, `NoEvents`, autosaved), or Unsubscribe from everything. Each email to members has a `Campaign.Topic`: newsletter for an issue, events when the admin picks About → Rides and events on Email members, none for club news (dues, waivers), which only a full unsubscribe stops. Unsubscribe links carry `&from=<topic>`: the page offers that kind first, and Gmail's one-click stops just that kind.
- **Renewing on `/join`** (`renewal.go`): for an address already on the list nothing typed is used straight away (anyone can type any email). It's kept as `Member.PendingJoin` (30 days) and the address gets "Finish renewing" (Confirm it's me); Confirm applies it: waiver, riders under 18, Family adults, blank details filled in. The form's answer is the same for every listed address ("This email is already on our list."), no name, dues or PayPal button, so it reveals nothing about the member. Admin Members shows "Renewal not confirmed". The plan they picked (`PendingJoin.Plan`) applies on Confirm through `planFor`: an email-list-only address takes it; Individual → Family when their dues are unpaid or run out within 60 days (`planWindow`), so the listed adults are added; Family never drops to Individual there (an admin does that, since household riders would lose cover).
- **Dues:** PayPal payment links (admins press Mark paid), or with `STRIPE_SECRET_KEY` + `STRIPE_WEBHOOK_SECRET` set, card payments through Stripe Checkout that mark members paid themselves (see Stripe below); the site never touches card data. A website joiner's welcome email goes once they're both marked paid and confirmed, in either order (`TakeWelcome`, `welcomeIfDue`); its `{ride_tips}` adds the live "Rides coming up that suit you" list (`ridesFor`). Waivers are yearly (Jan–Dec), drawn or typed signature, minors signed by a parent/guardian, Family members' other adults get private `/membership?t=` links.
- **Stripe** (`stripe.go`, no Stripe library: form posts to the API, HMAC webhook check): `payLink` (used for every Pay button, `{pay_link}`, the confirm email's pay line and the join result) is `/pay/<member>.<sig>` (`payCode`, HMAC of the store secret; never expires, only lets someone pay, so it's safe to forward; a Family rider's goes to the plan holder's). **Joining:** with Stripe on, the join answer carries `go` and `pay_url` = the pay link + `?from=join`, and site.js goes straight there after showing the result (no new tab; without JS the result's button goes there); `from=join` rides through the pay form into Stripe's success/cancel URLs, and coming back paid shows "Welcome to PaxVelo, <first>!" (`payData.Welcome`: plan, Good through, a Confirm your email alert while unconfirmed, `ridesFor` their level, Calendar / Bike Safety 101 / My Membership). GET shows "<year> <plan> dues" with Pay $N; while the plan's `PAYPAL_*_URL` is also set it shows "Pay $N by card" and "Pay with PayPal" side by side and waits for a pick (PayPal payments still need Mark paid). **Card / PayPal / Both** switch at the top of Treasurer → Payments (`payWays`, `Store.PayWith`: "card", "paypal", "" = both; `POST /admin/treasurer/payments/with`, board): a way not set up in the conf is greyed out, and switching one off only counts while the other is set up. PayPal only: `payLink` is the PayPal link again, `/pay/<code>` 303s to it (a return from Stripe with `?session=` is still finished) and POST starts no checkout; the webhook keeps working while the keys are set. Card only, the button is pressed for them by site.js (`form[data-auto]`, like Confirm; not after `?back=1` from Stripe's Cancel, not when paid). POST (sameOrigin, 20/hour/IP) creates a Checkout session (`mode=payment`, `price_data` at `DUES_*`, `metadata[member|kind=dues|plan]`, `customer_email`) and 303s to `checkout.stripe.com` (public CSP `form-action` allows it); each start is kept as a `StripeCheckout` (`Store.Checkouts`, 180 days, `From` join/pay, `Paid` set by `RecordStripe`); `Unfinished(m)` = their latest one unpaid with no payment since (Payments, member page, Finish paying email). Paid up: the page shows Good through, plus Renew now within 60 days of running out (`renewWindow`). Stripe's answer comes two ways, either enough: `POST /stripe/webhook` (`Stripe-Signature` checked against `STRIPE_WEBHOOK_SECRET`, 5 min tolerance; only `checkout.session.completed`/`async_payment_succeeded` with `kind=dues`; a failure answers 500 so Stripe retries) and the return to `/pay/<code>?session=cs_…` (must be that member's session). Both re-read the session from Stripe (`checkSession`, expanding the fee) and `RecordStripe` once per session id (`Store.Payments`, `StripePayment`: member, year, cents, Stripe's fee or 2.9% + 30¢ when it hasn't said, `Via`, `Mode=test`); a new one adds `nextPaidYear` (a year more when paid up) and runs `afterPaid` (welcome email when due, Family waiver links, as Mark paid) and `alertPaid` (admin phones, Members alerts). A new payment also runs the automations straight away (Thanks for renewing, from 9 am). **Admin:** Treasurer → Payments (`stripeadmin.go`, `money-payments`, board): the year's card payments (count, new vs renewals, Stripe fees, net; table with a Stripe dashboard link per payment, test/renewal/deleted tags, ≈ on worked-out fees), Started, not paid (last 30 days, `unfinishedFor`), Spreadsheet (`payments.csv`), alerts for keys missing or test mode, and the Card / PayPal / Both switch. The member page's Dues card lists their card payments and "Started paying …, not finished". Undo on the member still removes the year; refunds are done in Stripe's dashboard and undone by hand. Tests: `stripe_test.go` with a fake Stripe server (`STRIPE_API`). Try it locally with test keys and `stripe listen --forward-to 127.0.0.1:<port>/stripe/webhook` (its whsec), or without the CLI: the return page alone marks them paid.
- **Member standing** (`memberstanding.go`): admin Members/Home count by dues, not the email list: Current members (dues not expired), Not paid yet (expired, or joined on the website), Email list only (never paid; Squarespace exports include newsletter sign-ups). The president can tick and **Delete them** (waivers are kept; `relinkWaivers` gives them back to whoever is added later with the account email, at startup and on every new member; an email change records the new one on their waivers as `Account`, keeping `Email` as signed), and fix years paid, join date and email status in a member's Membership record box (sends nothing).
- **Site-move email** (`moved.go`): for members who paid on the old site. Members → tick → **Mark paid & send site-move email** (or the member page button) marks them paid if needed and sends it instead of the welcome (`MovedSent` records it). Editable on Email. `{dues_expire}` = `DuesExpire`: the join day, the year after the last year paid; shown on the member list, member page and /membership ("Good through"). **Paid follows the expiry** (`dues.go`): `Member.Paid()` is today ≤ `DuesExpire`; `PaidYears` are membership years from the join day. Mark paid adds `nextPaidYear` (new member: a year from joining; lapsed: the year ending 6–18 months out); "Renew early" on a member page adds a year; Undo removes the latest year. Join days use `TIMEZONE` (`clubTZ`). Waivers stay Jan–Dec.
- **Club kit** (`kit.go` store, `kitpage.go` public `/kit`, `kitadmin.go` + `admin-kit.html` Website → Club kit, board only): the yearly Jakroo bulk order. `Store.Kit` (`KitShop`): items the board builds (photo, `MemberPrice` = subsidized, `Price` = regular, sizes, hidden; unpriced = not shown; seeded jersey + bibs once), order window (`Open` + `Closes`), `PayURL` (a PayPal.me link gets `/<total>USD` added, `PayLink`), `Round` (Start next year's order; old orders kept, `?round=`). Members order from `/kit?t=<token>` (`{kit_link}` placeholder; **Write the kit email** fills the Email members draft; cookie `pv_kit` on `/kit`; My Membership shows the order while open); only paid-up members (`Member.Paid`) get the form; one `KitOrder` per member per round, lines keep name and price as ordered, changeable until it closes or is marked paid. Admin: Mark paid, totals by item and size (`Tally`), CSV. kit.md's words wrap the store (Intro above, Body below); removing kit.md makes `/kit` the team store again.
- **RSVPs** (`rsvp.go` store, `rsvppage.go` public, `rsvpadmin.go` + `admin-rsvp.html`; Email → RSVPs, every admin): invitations members answer (`Store.RSVP`, `RSVPEvent`: title, date, time, place, details, `AskBringing`, `Closes`, `Closed`; `RSVPReply` per member: answer yes/maybe/no, `Guests` + `Who`, `Bringing`, note). Each email's `{rsvp_<id>}` (`rsvpLinks` in `personalize`) is the member's `/rsvp/<id>?t=<token>`; open ones are offered in the Send an email editor (`EmailPieces`, `rsvpPieces`). **Write the invitation email** fills the draft (`rsvpInvitation`). The page is noindex, `Referrer-Policy: same-origin` (not no-referrer: that sends `Origin: null` and `sameOrigin` blocks the post), shows place/details only from a member's link, and from one the guest list (`Going`: yes then maybe, name, +guests, who, bringing; off with `HideGuests`, "Members see who’s coming") and Add to my calendar (`/rsvp/<id>/calendar.ics?t=` and `/rsvp/<id>/google?t=`, a redirect to Google Calendar; 2 h, or all day without a time; also `{rsvp_<id>_calendar}` / `{rsvp_<id>_google}` in emails, written into the invitation), and the Where card's Directions + Add to calendar buttons (`appleDevice` by User-Agent: Apple Maps and the .ics on iPhone/iPad/Mac, else Google Maps and Google Calendar; "Also:" the others plus Waze; maps get `MapAddress`, the place from its first part starting with a number; the email's `{rsvp_<id>_directions}` is `/rsvp/<id>/directions?t=`, which picks the same way), saves nothing from a test email's `test` token; answers change until `IsOpen` ends (closed, past `Closes`, or after the day). Admin: counts (coming incl. guests), who's bringing what, current members who haven't answered, CSV (`csvSafe`), remove answers (a row's Remove, or tick several → the Members-style `bulk-bar` → Remove them; Undo, `RSVPBook.Dropped`), Remove the invitation (in the actions and on each list row; Undo, no confirm, like Treasurer lines; every Undo notice shows only on the page a Remove returns to, `?undo=1`/`justRemoved`, never again later). **On the club calendar** (`rsvpcal.go`): "On the calendar" on the invitation form ties it to a calendar event (`RSVPEvent.Ride`, a RideOcc key; events only, not rides; preselects the only event on its day, `guessRide`; an empty date takes the event's). The calendar then shows the head count on the event (`cal-lead`) and in its hover card who's coming with +guests and what they're bringing (`cal-pop-rsvp`, `RideOcc.RSVP`, short names via `shortName`, first 8; a hidden guest list = counts only). The event page gets an RSVP section (shared templates in `rsvp-parts.html`: `rsvp-answer`, `rsvp-guests`) with Directions / Add to calendar / Share; from a member's link (`?t=`) it's their form (posts with `back=<key>` and returns there), full names and the private place; anyone else gets "Email me my link" (`POST /rsvp/<id>/link`, same answer for any address, 5/hour/IP, 3/hour/address; the email links to the event page). The RSVP page links to the event. **Day-before reminder** (`rsvpreminder.go`, built-in row "RSVP reminder" on Email → Automations, editable, switch = `RSVPBook.ReminderOff`, deletable like the other built-ins): from 9 am the day before (catching up until the day), each yes/maybe answer gets it once (`RSVPReply.Reminded`, marked first, kept when the answer changes); pieces `{event} {when} {your_answer} {place_line} {directions} {rsvp_link}` (`fillRSVPReminder`); an invitation skips it with "Remind them the day before" unticked (`NoReminder`); the event page shows "Reminder <day>" / "Reminder sent to N". The answers table is `tight cards` (cards on phones).
